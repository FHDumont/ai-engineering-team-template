# Setup

Roda na primeira sessão de um repo novo, depois do merge do PR de adoção e na migração de repo com processo parecido. É obrigatório: o setup pendente é o primeiro passo da sessão, antes de qualquer outro pedido (`process-design` §2, regra 1).

1. Rode `scripts/setup-repo.sh --dry-run` e `scripts/setup-repo.sh --offers` para ver o que falta. Na migração, rode `gh variable list`: se `CI_RUNS_ON` já existir, não faça a pergunta do runner. O `--dry-run` lista cada check exigido que sairia, cada `strict` que afrouxaria, cada label em uso que seria renomeada ou apagada e a entrada no modo sem proteção. Sem ok do dono isso não se aplica e o `--check` fica sujo.
2. Faça **um quadro de escolha** (`AskUserQuestion`, uma pergunta por decisão): nome e objetivo; stack; lab; bots; onde ficam os segredos; runner próprio na máquina do dono do repo; quadro do GitHub Projects; meta de tempo; limites da máquina (só se for a primeira vez nela); se o headless fica ligado (padrão: desligado; grave `on` em `.github/headless` só com o sim). Se o dry-run listou afrouxamento, peça o ok de cada um. Para os segredos, a pergunta é só "Criar o `.env` para você?" (a alternativa opcional é a conta de serviço do gerenciador de senhas; veja `docs/BOTS.md`). Os segredos são um quadro só, com essa única pergunta; nunca uma pergunta de provedor seguida de outra de arquivo.
3. Nada é criado no GitHub sem um "sim" no quadro, e nada é dado como criado sem ler de volta (`process-design` §2.1). Aplique só o que foi aceito:
   - padrão do repo: `scripts/setup-repo.sh` (com `--owner-ok` só depois do quadro que autorizou check a sair, `strict` a afrouxar, label em uso ou modo sem proteção);
   - quadro: confira `gh auth status`; sem `project` (que inclui a leitura), pare em `esperando você` com um comando só para o dono rodar, o da linha `next:` de `scripts/setup-repo.sh --project` (`gh auth login -h github.com -p https -w -s gist,project,read:org,repo,workflow`, sempre com a lista completa de escopos); o agente nunca roda esse comando, nunca digita o código nem preenche o campo, e nunca pede nem roda `gh auth refresh`, `gh auth logout`, `gh auth setup-git` ou `--with-token`. Na volta, confira o escopo de novo e rode `scripts/setup-repo.sh --project` (idempotente: vincula, cria as views que faltam, lê os workflows). Cada linha `pending:` a sessão faz no mesmo navegador (view recusada, workflows nativos *Auto-add to project*, *Item added to project*, *Item closed* e *Pull request merged*); só declare pronto depois de ler de volta o quadro (`gh project view <n> --owner <dono>`), o vínculo no repo, as views pelo nome e layout e os workflows ligados;
   - recusas: `scripts/setup-repo.sh --decline project|runner|runner-trigger`;
   - runner: `scripts/setup-runner.sh --dry-run` mostra os passos. Com o "sim" do quadro, se você alcança a máquina do lab, rode você mesmo `scripts/setup-runner.sh --register` (`--dir`, `--name` e `--label` se couber) e só declare pronto depois de ler de volta `gh api repos/<slug>/actions/runners` (runner online) e `gh variable get CI_RUNS_ON`. Se o dono precisar rodar à mão (máquina que você não alcança), o passo a passo aponta só o script `scripts/setup-runner.sh --register`, nunca comandos soltos (`config.sh`, `svc.sh`, `curl` do pacote, token do `gh api`).
   - `.env` com "sim": rode `scripts/init-env.sh` (cria `~/.<repo-slug>/.env`, pasta 700 e arquivo 600, só com as chaves vazias `BOT_WEBHOOK_<SLUG>_URL=`, `_SECRET=`, `GH_APP_BOT_<SLUG>_TOKEN=` e `GH_APP_METHOD_TOKEN=`). Peça ao dono do repo para abrir o arquivo que o script imprimiu e colar os valores. O agente nunca lê nem escreve valores. Depois confira com `source scripts/lib/secret.sh; secret_ready BOT_WEBHOOK_<SLUG>_URL` de cada bot escolhido (só o código de saída, nada é impresso).
   - **GitHub Apps por papel** (o dono cria; o agente nunca cria App, chave nem segredo). Uma App do agente do método (`metodo-agente`) e uma por bot (`<slug>`), com issues e pull requests em escrita. O token vai nas chaves acima. Com o token, os comentários saem como a App; sem ele, como o `gh` do dono. `ROLE_APP_REQUIRE=1` recusa até a App existir. Guia no README.
   - **Meta de tempo** (pergunta do quadro, só aqui: nenhuma fase pergunta nem lê a meta). Explique em uma frase: a fase deve ter mediana abaixo de X min, sem contar a espera pelo dono, e o `validate.sh` abaixo de Y s; acima disso a gerenciadora conversa com o dono no fim do grupo (skill `integrate`). Ofereça o padrão do método (45 min e 240 s) ou valores do dono. Grave em `.github/time-targets.tsv` (colunas `phase`/`validate`, valor, unidade `min`/`s`, separadas por tab; edite só as duas linhas, mantendo os comentários) e leia de volta. Padrão aceito: não mexa no arquivo.
   - **Limites da máquina** (só na primeira vez nesta máquina: sem a linha `# setup: confirmed` em `~/.config/ai-method/machine-limits.env`; com ela, não pergunte, pois valem para todos os projetos). Mostre o padrão e o que cada um faz: `AI_METHOD_SLOTS_VALIDATE` (2: `validate.sh` ao mesmo tempo, somando todos os projetos), `AI_METHOD_SLOTS_FASE` (3: fases abertas ao mesmo tempo na máquina) e `AI_METHOD_TEST_JOBS` (CPUs ÷ vagas de validate: testes em paralelo dentro de um `validate.sh`). Ofereça manter ou ajustar; ajustou, edite os valores no arquivo (rode antes `scripts/machine-slots.sh --status` se ele ainda não existir). Nos dois casos acrescente a linha `# setup: confirmed` e leia o arquivo de volta. Depois disso o dono só é chamado quando o fim do grupo acusa over-target.
4. Registre nome, objetivo e stack em `docs/STATE.md`. O setup só acabou quando `scripts/setup-repo.sh --check` sai 0. Uma resposta "Upgrade to GitHub" não grava o modo sem proteção sozinha: só o ok do dono, depois `--owner-ok`. Com o modo gravado, diga em uma frase que o portão passa a ser de script e que o GitHub não impede um merge feito à mão (`process-design` §10.5).
5. Termine com a saída de `scripts/status.sh` colada como está (três linhas em negrito, sem bloco de código).
